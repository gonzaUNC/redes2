Capa de Enlace de Datos
Convierte un canal físico propenso a errores en un servicio de comunicación local ordenado. Opera salto a salto. Gestiona tramas, errores, acceso al medio y la arquitectura de switches.
📦
Naturaleza y alcance — ¿Qué hace la capa de enlace?
▼

La capa de enlace toma el flujo de bits y los organiza en tramas. Su operación es estrictamente local: solo se preocupa por entregar la trama al nodo vecino inmediato.

Definición clave
Una trama es la unidad de datos de la capa de enlace. Encapsula el paquete de red añadiéndole encabezado (MACs) y verificación de errores (FCS/CRC).
CapaUnidadAlcance
Físicabit/señalMedio físico
EnlacetramaEnlace local (salto a salto)
RedpaqueteExtremo a extremo
TransportesegmentoProceso a proceso
🔲
Formatos de trama — Ethernet II vs IEEE 802.3
▼
Ethernet II / DIX
  • Campo de 2 bytes: EtherType
  • Identifica protocolo superior (IPv4=0x0800)
  • Valor ≥ 1536 (0x0600)
  • Más común en la práctica actual
IEEE 802.3
  • Campo de 2 bytes: Longitud
  • Indica cuántos bytes hay en el campo de datos
  • Valor ≤ 1500
  • Si ≤ 1500 → longitud; si ≥ 1536 → tipo
Estructura de trama Ethernet
Preámbulo (7B) | SFD (1B) | MAC Destino (6B) | MAC Origen (6B) | Tipo/Long (2B) | Datos (46-1500B) | FCS (4B)
✅
Control de flujo y confiabilidad en la capa de enlace
▼

Entramado: delimitar unidades de datos dentro de un flujo de bits.

ACK + Timeout: el emisor pone un temporizador. Si el ACK no llega, retransmite. Los números de secuencia permiten descartar duplicados.

Piggybacking
Incluir el ACK de confirmación dentro de una trama de datos que va en sentido contrario, ahorrando una trama de control independiente.

CSMA/CD — Secuencia en colisión
1. Escucha el canal (Carrier Sense)
2. Si libre, comienza a transmitir
3. Sigue escuchando (Collision Detection)
4. Si detecta colisión → para y envía JAM (48 bits)
5. Espera tiempo aleatorio (Binary Exponential Backoff) y reintenta
📐
Tamaño mínimo de trama — Condición de seguridad CSMA/CD
▼
Condición de seguridad
El tiempo de transmisión de la trama debe ser al menos el doble del tiempo de propagación máximo entre los nodos más alejados: T_tx ≥ 2τ → L_min ≥ R × 2τ
Ejemplo Ethernet 10 Mbps: L_min = 10×10⁶ b/s × 2 × 25μs = 500 bits = 62.5 bytes → estándar: 64 bytes
Relleno (Padding)
Si los datos son menos de 46 bytes (payload mínimo para alcanzar 64 bytes totales), la capa de enlace agrega bytes de relleno. El receptor los descarta.

Hubs vs Switches — La evolución del hardware
▼
DispositivoCapaFunciónImpacto
HubFísicaRepite señales a TODOS los puertosUn único dominio de colisión, half-duplex obligatorio
SwitchEnlaceAlmacena y reenvía analizando MAC destinoSepara dominios de colisión; full-duplex posible

Aprendizaje dinámico del switch: observa MAC de origen → aprende el puerto. Si la MAC destino es conocida → reenvía solo por ese puerto. Si no → flooding por todos salvo el de entrada.

Flooding ≠ Broadcast
Flooding: decisión interna del switch ante desconocimiento de MAC. Broadcast: solicitud explícita de la trama (MAC destino = FF:FF:FF:FF:FF:FF).
📡
IEEE 802.11 — WiFi
Opera bajo lógica fundamentalmente distinta a Ethernet. El medio inalámbrico impide detectar colisiones mientras se transmite, por lo que WiFi usa CSMA/CA (evitación). Cada trama de datos requiere ACK explícito del receptor.
🏗️
Arquitectura — Ad Hoc vs Infraestructura
▼
Red Ad Hoc (IBSS)
  • Nodos se comunican directamente
  • Sin estación base centralizada
  • Modo distribuido puro
Red con Infraestructura (BSS)
  • Hosts se asocian a un Punto de Acceso (AP)
  • AP actúa como puente hacia red cableada
  • Varios BSS conectados = ESS
🚫
¿Por qué no CSMA/CD en WiFi? Las 3 razones
▼
  1. Saturación del receptor: la señal propia transmitida es mucho más fuerte que cualquier señal entrante. No podés escuchar interferencias mientras transmitís.
  2. Diferencia de visión del canal: lo que escucha el transmisor no es lo que escucha el receptor. El canal inalámbrico no es uniforme.
  3. Detección débil: identificar una colisión en el mismo canal mientras se transmite es tecnológicamente complejo y costoso.
Consecuencia
WiFi no puede confirmar si hubo colisión. Por eso cada trama recibida debe ser confirmada con un ACK. Sin ACK → se asume colisión o error → retransmisión.
⚙️
CSMA/CA — Mecanismos de control
▼

NAV (Network Allocation Vector): detección virtual. Temporizador local que indica cuánto tiempo estará reservado el canal, basado en el campo Duration de las tramas de control escuchadas.

Backoff aleatorio: la estación elige k al azar entre [0, CW-1]. El contador decrece cuando el canal está libre, se congela cuando está ocupado.

Ventana de Contención (CW)
Cada intento fallido duplica la CW (Binary Exponential Backoff). Reduce la probabilidad de que dos estaciones elijan el mismo slot y vuelvan a colisionar.
👁️
Estación Oculta y Estación Expuesta
▼
Estación Oculta
Situación: A y C no se escuchan entre sí, pero ambas están en rango de B.
Problema: A y C transmiten simultáneamente a B → colisión en B.
Solución: RTS/CTS. B responde al RTS de A con un CTS que informa a C que el canal está reservado.
Estación Expuesta
Situación: B transmite a A. C escucha a B y cree que el canal está ocupado, así que no transmite a D.
Problema: la transmisión de C a D no interferiría, pero C se abstiene innecesariamente → subutilización del canal.
🎛️
DCF vs PCF — Funciones de coordinación
▼
DCF — Distributed Coordination Function
  • Modo estándar y distribuido
  • Todas las estaciones compiten por el canal
  • Secuencia: RTS → CTS → DATA → ACK
  • Requiere DIFS antes de transmitir
PCF — Point Coordination Function
  • Modo centralizado con AP
  • AP coordina mediante polling
  • Elimina colisiones internas
  • Usa PIFS para ganar acceso antes que DCF
Prioridades temporales: SIFS < PIFS < DIFS
SIFS: el más corto → máxima prioridad. Para ACKs, CTS.
PIFS: intermedio → el AP lo usa en modo PCF.
DIFS: el más largo → estaciones en contención esperan DIFS.
📊
Tasa Efectiva vs Tasa Física
▼
Fórmula
R_eff = Bits útiles de datos / Tiempo total (incluyendo todo el overhead)

El tiempo total incluye: tramas de control (RTS, CTS, ACK), trama de datos, intervalos SIFS/DIFS, backoff aleatorio.

Importante en examen
La tasa efectiva siempre es menor que la tasa física. Hay que sumar todos los intervalos. Solo el payload cuenta en el numerador.
🌊
Control de Flujo en la Capa de Transporte
Evita que un emisor rápido desborde la capacidad de procesamiento de un receptor lento. Opera extremo a extremo. El receptor informa cuánto espacio tiene disponible y el emisor se autorregula.
🆚

▼

💾
¿Por qué el receptor necesita búferes?
▼
  1. Disparidad de velocidad: el emisor puede generar datos más rápido de lo que la aplicación los consume.
  2. Eficiencia en el procesamiento: acumular segmentos para procesarlos en lotes reduce la sobrecarga del sistema.
  3. Gestión de desorden: los segmentos pueden llegar fuera de secuencia y deben almacenarse hasta completar el orden correcto.
🤝
Protocolo dinámico de "Pedir y Otorgar" (Créditos)
▼
  1. Solicitud: el emisor pide una cantidad inicial de búferes.
  2. Concesión (Grant): el receptor otorga un número específico según su carga actual.
  3. Contador de crédito: el emisor lleva un contador. Cada segmento enviado resta 1. Si llega a 0, se detiene hasta recibir más espacio.
Deadlock (Estancamiento)
El segmento de reserva de búferes se pierde. El emisor espera permiso, el receptor cree haberlo dado ya.

Solución: cada host envía periódicamente el estado actual de sus búferes y ACKs acumulados.
🔧
Control de flujo en TCP — Optimizaciones
▼

Secuenciación por bytes: el número de secuencia representa la posición del byte en el flujo, no el número del paquete.

Anuncio proactivo (rwnd): el receptor anuncia su espacio disponible en cada ACK. No hay que solicitar permiso explícito.

Búfer circular: cuando la aplicación lee datos, libera bytes del inicio del búfer y habilita espacio nuevo al final.

Ventana efectiva de envío TCP
Ventana efectiva = min(rwnd, cwnd)
rwnd = control de flujo (capacidad del receptor)
cwnd = control de congestión (capacidad de la red)
⚡
Control de Congestión en TCP
Evita el colapso de la red cuando la demanda supera la capacidad de los routers. TCP infiere la congestión a través de pérdidas y ajusta dinámicamente cuántos datos puede tener "en vuelo". La estrategia central: AIMD.
🚨
¿Qué es la congestión y cómo se produce?
▼
  1. Saturación: el tráfico entrante supera la capacidad del router.
  2. Desbordamiento: los búferes se llenan por completo.
  3. Descarte: el router tira paquetes → el emisor retransmite → más tráfico → ciclo de colapso.
📈
Slow Start y Congestion Avoidance
▼
Slow Start — Arranque Lento
A pesar del nombre, busca alcanzar rápidamente la capacidad mediante crecimiento exponencial.
• Inicio: cwnd = 1 MSS
• Por cada ACK recibido: cwnd += 1 MSS → se duplica cada RTT
• Se detiene cuando cwnd alcanza ssthresh
Congestion Avoidance
Una vez que cwnd ≥ ssthresh, el crecimiento pasa a lineal:
• cwnd += 1 MSS por cada RTT completo
• Implementa la parte "Additive Increase" de AIMD
⚔️
TCP Tahoe vs TCP Reno — La evolución crítica
▼
TCP Tahoe (1988)
  • Ante cualquier pérdida (timeout O 3 ACKs dup)
  • ssthresh = cwnd / 2
  • cwnd = 1 MSS — reinicia desde cero
  • Patrón: dientes de sierra grandes
TCP Reno (1990)
  • Distingue el tipo de pérdida
  • Por Timeout: igual que Tahoe (cwnd = 1)
  • Por 3 ACKs dup: Fast Recovery → cwnd = ssthresh
  • Patrón: dientes de sierra pequeños y frecuentes
EventoTahoeReno
3 ACKs duplicadoscwnd = 1, Slow Startcwnd = ssthresh, Fast Recovery
Timeoutcwnd = 1, Slow Startcwnd = 1, Slow Start (igual)

El Problema de los Duplicados Retrasados
Segmentos que permanecen en la red más tiempo del esperado pueden llegar al receptor fuera de su contexto original, siendo confundidos con datos nuevos. La regla: nunca se pueden entregar duplicados a la aplicación.
🔢
Números de secuencia y el problema del espacio finito
▼

La solución viable es identificar cada segmento con un número único. El problema: el espacio es finito → los números se reutilizan (ciclan) → ambigüedad.

Ejercicio de dimensionamiento: Segmentos de 1500 B, tasa = 10 Mbps, T = 30 s 1. Bits totales en T: 10⁷ × 30 = 3×10⁸ bits 2. Bits por segmento: 1500 × 8 = 12.000 bits 3. Segmentos máximos en T: 3×10⁸ / 12.000 = 25.000 segmentos 4. Bits necesarios: log₂(25.000) ≈ 14.6 → se necesitan al menos 15 bits
🔑
ISN — Número Inicial de Secuencia
▼
ISN Aleatorio (Comer)
  • Se elige un número aleatorio de 32 bits al crear la conexión
  • El rango enorme hace extremadamente improbable coincidir con un duplicado
  • Simple de implementar
ISN Atado al Reloj (Tanenbaum)
  • Un contador binario se incrementa en intervalos uniformes
  • El reloj avanza monótonamente → cada conexión usa números posteriores
  • TCP usa pulsos de ~4 μs con 32 bits para T=120s
🌐
Organización y Reenvío en Interredes
Una interred conecta múltiples redes heterogéneas. Los mecanismos clave: fragmentación, entunelamiento y agregación de prefijos.
✂️
Fragmentación — Gestión de diferentes MTUs
▼
Fragmentación Transparente
  • La puerta de enlace de salida reensambla
  • La red siguiente ve el paquete completo
  • Problema: todos los paquetes deben salir por la misma puerta
Fragmentación No Transparente (IPv4)
  • El reensamblado ocurre SOLO en el host destino
  • Cada fragmento viaja independientemente
  • Más flexible para enrutamiento
Campos IPv4 para fragmentación
Identificación (ID): valor común para todos los fragmentos del mismo datagrama
Bit MF (More Fragments): 1 = hay más fragmentos; 0 = último fragmento
Offset: posición del fragmento en el original, en unidades de 8 bytes
Bit DF (Don't Fragment): si está en 1, prohíbe la fragmentación
🕳️
Entunelamiento — Encapsulación de identidad
▼
¿Qué es?
Permite transportar un paquete de protocolo X a través de una red que solo entiende el protocolo Y, encapsulando el paquete X dentro de un encabezado Y. La red intermedia lo ve como tráfico Y normal.
Analogía
Es como meter una carta (paquete IPv6) dentro de un sobre con dirección diferente (encabezado IPv4). El cartero (red IPv4) solo ve el sobre exterior y lo entrega.
🗜️
Agregación de Prefijos — Escalabilidad del enrutamiento
▼
Cómo funciona
Se buscan los bits más significativos comunes entre varios prefijos para crear una entrada agregada que los cubra a todos. Por ejemplo, 4 redes /22 se pueden agregar en una sola /20.

Impacto real: la agregación puede reducir las tablas de los routers globales en aproximadamente 200.000 prefijos. Sin esto, Internet a escala actual sería imposible.

🗺️
WAN Jerárquica y Protocolo OSPF
Las WAN grandes no pueden usar protocolos de estado de enlace "planos". La solución: jerarquía. Dividir la red en áreas con un Área Dorsal (Área 0) como eje central.
👥

🔷
Dijkstra modificado — DAG en lugar de árbol
▼
La diferencia clave
El Dijkstra clásico guarda UN solo predecesor por nodo → árbol.
OSPF guarda el conjunto de todos los predecesores que resultan en costo mínimo → DAG (Grafo Acíclico Dirigido).

Esto permite múltiples rutas de igual costo hacia un mismo destino, habilitando balanceo de carga (ECMP — Equal Cost Multi-Path).

🛰️
Enrutamiento en Interredes — BGP
El enrutamiento exterior entre Sistemas Autónomos no busca la ruta globalmente óptima. BGP conecta SAs mediante políticas administrativas que reflejan acuerdos comerciales y soberanía de red.
🏛️
El modelo de dos niveles — IGP vs BGP
▼
IGP / PPEI (ej: OSPF, IS-IS)
  • Opera dentro de un Sistema Autónomo
  • Métricas internas (costo de enlace)
  • No se expone al exterior
EGP / PPEE — BGP
  • Opera entre Sistemas Autónomos
  • Protocolo común para toda Internet
  • Sesiones TCP punto a punto (puerto 179)
  • Guiado por políticas administrativas

Ej. 1
Fragmentación IP — Campos DF, MF y Desplazamiento en 3 enlaces
▼
Host A → R1 → R2 → Host B. Mensaje TCP: 900 B datos + 20 B encabezado TCP. Encabezado IP = 20 B. MTUs: A-R1 = 1024 B (enc. trama 14 B), R1-R2 = 512 B (enc. 8 B), R2-B = 512 B (enc. 12 B).
Cálculo del payload disponible por enlace

Payload IP disponible = MTU de trama − encabezado de trama − encabezado IP:

  • Enlace A-R1: 1024 − 14 − 20 = 990 B de payload IP disponibles
  • Enlace R1-R2: 512 − 8 − 20 = 484 B de payload IP disponibles
  • Enlace R2-B: 512 − 12 − 20 = 480 B de payload IP disponibles

El datagrama original tiene 900 + 20 (TCP) = 920 B de datos IP (payload de IP).

Enlace A → R1 (payload máx. 990 B)

920 B ≤ 990 B → no se fragmenta. Se transmite un único datagrama IP.

Paquete 1: Long. total = 940, ID = x, DF = 0, MF = 0, Desplaz. = 0
Enlace R1 → R2 (payload máx. 484 B)

920 B > 484 B → hay que fragmentar. El offset se mide en unidades de 8 bytes, por eso el tamaño de fragmento debe ser múltiplo de 8: 484 → redondear a 480 B (múltiplo de 8).

  • Fragmento 1: 480 B de datos → Long. total = 480+20 = 500, MF = 1, Offset = 0
  • Fragmento 2: 920 − 480 = 440 B de datos → Long. total = 440+20 = 460, MF = 0, Offset = 480/8 = 60
Frag 1: Long=500, ID=x, DF=0, MF=1, Offset=0 Frag 2: Long=460, ID=x, DF=0, MF=0, Offset=60
Enlace R2 → B (payload máx. 480 B)

Los fragmentos ya llegan con 480 B y 440 B de datos respectivamente. Ambos caben (480 ≤ 480 y 440 ≤ 480), así que no se fragmenta más. Los mismos dos fragmentos se reenvían sin cambios.

Regla clave
El campo ID es el mismo para todos los fragmentos del mismo datagrama original. El reensamblado ocurre solo en el host destino (fragmentación no transparente en IPv4).
Ej. 2
Algoritmo de reensamblado de fragmentos IP en el destino
▼
Describir una manera de reensamblar fragmentos IP en el destino. Asumir que llegaron todos los fragmentos.
Pseudocódigo de reensamblado
// Estructura de datos: tabla indexada por ID de datagrama tabla[ID] = { buffer[]: array de bytes, fragmentos_recibidos: set de offsets, total_bytes: -1 (desconocido hasta recibir MF=0) } Al recibir un fragmento: id = encabezado.identification offset_bytes = encabezado.fragment_offset * 8 datos = payload del fragmento longitud_datos = encabezado.total_length - 20 // Copiar datos en posición correcta tabla[id].buffer[offset_bytes .. offset_bytes+longitud_datos] = datos tabla[id].fragmentos_recibidos.agregar(offset_bytes) // Si es el último fragmento (MF=0), conocemos el tamaño total si encabezado.MF == 0: tabla[id].total_bytes = offset_bytes + longitud_datos // Verificar si tenemos todo si tabla[id].total_bytes != -1: bytes_acumulados = suma de todos los tamaños de fragmentos recibidos si bytes_acumulados == tabla[id].total_bytes: entregar tabla[id].buffer a la capa superior eliminar tabla[id] de la tabla
Puntos clave del algoritmo
El campo ID común permite asociar todos los fragmentos. El offset indica dónde ubicar cada fragmento en el buffer. El bit MF=0 del último fragmento revela el tamaño total esperado. Solo cuando se acumulan todos los bytes se entrega el datagrama completo.
Ej. 3
Agregación de prefijos — 57.6.96.0/21 a 57.6.120.0/21
▼
Subredes: 57.6.96.0/21, 57.6.104.0/21, 57.6.112.0/21, 57.6.120.0/21. ¿Pueden agregarse si usan la misma línea de salida?
Conversión del tercer octeto a binario
57.6.96.0/21 → tercer octeto: 96 = 0110 0000 57.6.104.0/21 → tercer octeto: 104 = 0110 1000 57.6.112.0/21 → tercer octeto: 112 = 0111 0000 57.6.120.0/21 → tercer octeto: 120 = 0111 1000 Bits comunes desde la izquierda: 011x xxxx → los primeros 5 bits son comunes

Los primeros dos octetos (57.6) son iguales para todos. En el tercer octeto, los primeros 5 bits son comunes: 011 y luego varían. Esto da un prefijo de 5 bits adicionales en el tercer octeto, es decir: 8 + 8 + 5 = /21... no, retomando: los 4 prefijos /21 juntos tienen sus 5 bits de prefijo en el tercer octeto, resultando en los primeros 8+8+5 = 21-3... veamos de otra forma.

Cuatro /21 consecutivos pueden agregarse en un /19: (4 redes de tamaño /21 = 2² × /21 → sube 2 bits → /19) Prefijo agregado: 57.6.96.0/19 Verificación: 57.6. 011 00000 .0/19 96 = 0110 0000 ✓ 104 = 0110 1000 ✓ 112 = 0111 0000 ✓ 120 = 0111 1000 ✓ Todos tienen los primeros 19 bits iguales.
Respuesta
Sí, se pueden agregar. El prefijo resultante es 57.6.96.0/19. Las 4 redes /21 son contiguas y comparten los primeros 19 bits de sus direcciones.
Ej. 4
Gap de 1024 direcciones en bloque agregado — Estrategia de tabla
▼
Bloque 29.18.0.0/17 (0.0 a 128.255). Gap de 1024 dir. desde 29.18.60.0 hasta 29.18.63.255, asignadas a una línea de salida diferente. ¿Hay que desagregar o hay alternativa?
Análisis del problema

Desagregar el bloque /17 en sus constituyentes sería muy costoso: implicaría decenas de entradas en la tabla de reenvío.

Solución alternativa más eficiente: mantener el prefijo agregado 29.18.0.0/17 para la línea de salida original, y agregar una entrada más específica para el gap:

  • 29.18.60.0 a 29.18.63.255 = 1024 direcciones = /22
  • Agregar entrada: 29.18.60.0/22 → nueva línea de salida
Tabla de reenvío: 29.18.60.0/22 → nueva línea de salida (más específico) 29.18.0.0/17 → línea de salida original (más general)
Clave: Longest Prefix Match (LPM)
El algoritmo IPv4 elige siempre la entrada con la máscara más larga (red más pequeña) cuando coinciden múltiples entradas. Así, las IPs del gap de 29.18.60.0 a 29.18.63.255 hacen match con /22 (más específico) y van a la nueva línea, mientras todo el resto del /17 sigue por la línea original. No es necesario desagregar.

Red de Regiones Jerárquica — Grafo de 5E, resúmenes, paquetes LSP
▼
Red de 5 regiones. Se pide: (1) qué grafo construye 5E, (2) qué hace 5A al recibir el resumen de la región 2, (3) paquete LSP de 5E, (4) paquete LSP de resumen que construye 2A.
1 — Grafo de 5E (router interno de Región 5)

Un router interno construye el grafo completo de su propia región y recibe resúmenes de las otras regiones. Por eso el grafo de 5E tiene dos partes:

  • Parte detallada: topología completa de la Región 5 (todos los routers 5A, 5B, 5C, 5D, 5E con sus enlaces y costos).
  • Parte resumida: para las Regiones 1, 2, 3, 4 → solo un nodo ficticio por región y el costo mínimo para llegar al router de borde de esa región (que llega como resumen vía el router de borde de Región 5).
2 — 5A recibe resumen de Región 2

El resumen de la Región 2 llega a 5A como un paquete LSP de resumen (construido por el router de borde de la Región 2). 5A lo incorpora a su grafo como un nodo abstracto de la Región 2, con el costo mínimo anunciado hacia esa región. Este nodo abstracto se usa en Dijkstra para calcular rutas hacia destinos de la Región 2.

3 — Paquete LSP del enrutador 5E

El LSP de un router interno anuncia sus vecinos directos y los costos de los enlaces hacia ellos.

LSP de 5E: Origen: 5E Vecinos: [(4C, costo), (5D, costo), (5A, costo)] Número de secuencia: N Tiempo de vida: TTL
4 — LSP de resumen que construye 2A

Un router de borde (2A) construye un LSP de resumen que anuncia los destinos de su región al resto de la WAN.

LSP de Resumen de 2A (para la Región 2): Origen: 2A (router de borde) Destinos internos de Región 2: [(2B, costo), (2C, costo), (2D, costo)] Costos: mínimos desde 2A hasta cada destino interno (calculados con Dijkstra dentro de la Región 2)

OSPF — Tareas de un enrutador de borde de área (ABR)
▼
Para OSPF, explicar qué tareas realiza un enrutador de borde de área (Area Border Router / ABR).
  • Participación en múltiples áreas: mantiene una Base de Datos de Estado de Enlace (BDEE) separada por cada área a la que pertenece, incluyendo el Área 0.
  • Construcción de LSAs de resumen (Type 3 Summary LSA): calcula los costos mínimos hacia los destinos internos de cada área y anuncia esos resúmenes a las otras áreas. Los routers internos de otras áreas ven solo el resumen, no la topología interna.
  • Inundación selectiva: inunda los LSAs de una área solo dentro de esa área. Nunca propaga LSAs internos de un área a otra (evita explosión de tráfico de control).
  • Cálculo de rutas inter-área: ejecuta Dijkstra (modificado, produciendo un DAG) sobre el grafo híbrido: topología detallada de sus áreas + resúmenes de las demás.
  • Construcción de tabla de reenvío: para destinos en otras áreas, identifica el nexthop correcto usando el camino calculado hacia el ABR de destino vía el Área 0.
Ej. 9
BGP — Tareas de un enrutador de borde de SA (ASBR)
▼
Para BGP, explicar qué tareas realiza un enrutador BGP (enrutador de borde de sistema autónomo).
  • Establecer sesiones eBGP: crea y mantiene sesiones TCP (puerto 179) con enrutadores de borde de otros SAs (peers externos).
  • Establecer sesiones iBGP: propaga dentro del propio SA las rutas aprendidas del exterior, comunicándose con otros enrutadores BGP internos.
  • Mantener las RIBs: gestiona la Adj-RIB-In (rutas recibidas), la Loc-RIB (mejor ruta seleccionada) y la Adj-RIB-Out (rutas a anunciar a vecinos).
  • Aplicar políticas de entrada y salida: filtra y modifica atributos (LOCAL_PREF, MED, AS_PATH) según la política administrativa del SA.
  • Seleccionar la mejor ruta: aplica el algoritmo de selección de BGP (8 criterios) para elegir la mejor ruta hacia cada prefijo.
  • Anunciar y retirar rutas: envía mensajes UPDATE con nuevas rutas accesibles o retira rutas que ya no son válidas.
  • Construir la tabla de reenvío: instala las mejores rutas BGP, resolviendo el NEXT-HOP via OSPF interno para encontrar el puerto de salida correcto.
Ej. 10
BGP — Selección de ruta y tabla de reenvío para prefijo x
▼
AS1, AS2, AS3, AS4. Todos ejecutan OSPF internamente y usan eBGP/iBGP entre SAs. El enrutador 1c aprende sobre el prefijo x.
Ítem 1 — ¿I = hacia 3a o hacia 1a?

Sin el enlace punteado AS2-AS4, la única ruta hacia x (que está en AS4) es a través de AS3: 1c → 1a → 3a → AS4. Por lo tanto I = 1a (el siguiente salto dentro del AS1 para salir hacia AS3 es 1a).

Ítem 2 — Con enlace AS2-AS4, ¿I = 3a o 1a?

Ahora hay dos rutas hacia x: vía AS3 (path = AS3, AS4) y vía AS2 (path = AS2, AS4). Ambas tienen longitud de AS_PATH = 2. BGP aplica los criterios en orden — si LOCAL_PREF y MED son iguales, se usa el AS_PATH más corto. Como empatan en longitud, se sigue con el criterio 6: costo IGP hacia el NEXT-HOP (hot-potato routing). 1c elige la salida más cercana según OSPF. La respuesta depende del grafo de AS1, pero el criterio determinante es el costo IGP menor.

Ítem 3 — Con AS5 intermedio, ¿I = 3a o 1a?

Rutas: vía AS2: path = AS2, AS5, AS4 (longitud 3). Vía AS3: path = AS3, AS4 (longitud 2). BGP elige AS_PATH más corto → vía AS3, por lo tanto I = 1a (el salto hacia AS3 dentro de AS1).

¿Cuál afirmación distingue correctamente control de flujo y control de congestión en TCP? Transporte

¿Cuál es el riesgo de que se pierda un segmento de control que solo anuncia nuevos búferes disponibles, en un protocolo genérico de reserva dinámica? Transporte
